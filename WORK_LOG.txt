--------------------------------------------------------------------------------
 SECTION 0 : OBJECTIVE
--------------------------------------------------------------------------------
 The project implements a 5-module computer-vision brief:

   A  Segmentation  - compare split-and-merge, watershed, Felzenszwalb, mean shift
   B  Calibration   - checkerboard intrinsics + 4 camera models for box size
   C  Motion        - hand-built dense Lucas-Kanade optical flow + speed
   D  Tracking      - constant-velocity Kalman filter, multi-object
   E  Recognition   - alignment / PCA-eigenbox / Hu-moment box classifiers
   +  pipeline.py   - integrates A -> B -> C -> D -> E

 Goal of the first work session:
   1. Run every module end to end and confirm it executes.
   2. Measure ACCURACY numerically, not just "it ran without crashing".
   3. Find and document bugs and weak spots.
   4. Produce a prioritised fix list.

 Key principle followed throughout:
   "It runs" is NOT the same as "it is correct".
   Every accuracy claim below is backed by a synthetic fixture with
   known ground truth, so there is a real number to compare against.

 SECTION 4 : WHY SYNTHETIC FIXTURES
--------------------------------------------------------------------------------
 The brief requires real footage for the final submission. Real footage was not
 available in this pass, so a synthetic clip with exactly known geometry was
 generated (tools/make_test_video.py, 45 frames, two rectangles moving 8 px/frame
 at 15 fps, i.e. a known 120 px/s). Fixtures were generated for calibration
 (14 tilted, 6 fronto-parallel checkerboards) and recognition (3 classes x 12
 crops).

 The point is not to substitute for real footage. It is that without a known
 answer there is no way to tell a working implementation from a plausible one,
 and every one of the five bugs in section 5 was invisible to the passing test
 suite and to visual inspection of the output.

   P1  -- CRITICAL  --  Kalman filter ~40 frame startup transient
   File   : module_d_tracking/kalman.py line 27
   Code   : self.state[:] = [x, y, 0.0, 0.0]
            self.covariance = np.diag([25.0, 25.0, 100.0, 100.0])
   Cause  : velocity starts at 0, so the filter must spend ~40 frames
            learning it. During that time the reported position lags badly.
   Measured (see the correction below - these RMSE values are unreliable):
             init v = 0      whole-run RMSE 6.10 px  (raw 1.60 px)
             init v = true   whole-run RMSE 1.12 px  (raw 1.60 px)
             45-frame clip: 4.77 px  vs  1.40 px

            40.0 -> 5.70 px), and the dt^4/dt^2 process-covariance fix does
            NOT help (6.37 px). Only the initialisation matters.
   CORRECTION, from section 9.2
            The RMSE values above scored both boxes against one box's geometry.
            The fixture's boxes differ in size and in y, so the second was scored
            against a centre ~20 px from its true one. Corrected: 20.55 / 25.45 px
            unseeded, 0.72 / 0.71 px seeded, peak unseeded error 44.5 px, and the
            unseeded filter is STILL 11 px behind at the end of the clip. The
            conclusion that only initialisation matters stands, and is stronger
            than the numbers here suggested.
   Fix    : when a track is created, seed the velocity from the displacement
            between the current detection and the previous frame's matched
            detection, and shrink P_vv accordingly. Module C already computes
            a belt velocity estimate, which can be used directly.

     The fix above is necessary but NOT sufficient, and the "5x" figure is far
     too conservative. Two reasons, both recorded in 9.2: gating the seed on the

     and the unseeded filter is still 11 px behind when the clip ends - see 9.2,
     which also corrects the first pass's 18.94 -> 0.13 px figures as a scoring

 9.2  P1  --  KALMAN STARTUP  -  FIXED, ~28x BETTER, AND THE NUMBERS RE-MEASURED
--------------------------------------------------------------------------------
 The log above attributed the transient to `self.state[:] = [x, y, 0, 0]`
 at kalman.py:27 and recommended seeding from the previous frame's detection.
 Implementing that alone did NOT work, and the reasons are worth recording:

   Attempt 1 - seed from the previous frame, gated on association_distance.
     No effect. A new track is created precisely BECAUSE the object failed
     association, so by construction the nearest previous detection is always
     farther away than the gate. The gate could never fire.

   Attempt 2 - widen the gate (seed_distance, default 3x association).

 9.3  P2  --  DENSE LUCAS-KANDE  -  FIXED AT THE ROOT, AND P2's FIX REVERSED
--------------------------------------------------------------------------------
 P2 as written in the log said: "use the translation component of
 fit_affine_flow, which is far more robust at larger motion (true 16 ->
 A-tx 13.35 vs median 6.63)."

 I implemented that first, and it did not deliver. Measuring the underlying flow
 field rather than the estimator on top of it showed why:

   true shift, single-level dense LK, median over valid pixels:
        1 px ->  1.00        3 px ->  2.75
        8 px ->  3.60       16 px -> -4.36

 The field is not merely noisy at 8 px, it is wrong by more than half, and it
 goes NEGATIVE at 16 px. Note this contradicts the log's own figure of "8 px ->
 1.68 px error" measured against a 10 px correlation length; on the smoke clip's
 much sparser texture the error is far worse. On the smoke clip the single-level
 median reports 1.58 px against a true 8.0 px - an 80% underestimate, not the
 21% the log recorded.

 Root cause is the ordinary one: brightness constancy is linearised around zero
 displacement, so a single-level solve is only valid for motion well inside one
 window width. fit_affine_flow cannot rescue this, because it fits the same bad
 field. It just fits it with less noise.

 FIX: coarse-to-fine Lucas-Kanade. The frames are put on a Gaussian pyramid and
 the solve runs coarse to fine, each level refining the previous level's flow
 warped onto the current level. `_dense_level` now takes an initial guess and
 warps the next frame by it before computing the residual, which is the standard
 formulation. Level count is automatic, capped so the coarsest level still has
 at least one full window of pixels; `max_levels` defaults to 5.

 MEASURED, known rigid shift of a textured synthetic frame, median flow:

   shift    1     2     3     5     8    12    16    24
   error  0.00  0.00  0.00  0.00  0.01  0.01  0.15  0.02

 Same measurement at 240x320, 180x320 and 120x160 agrees, so the automatic level
 choice is not tuned to one resolution.

 On the smoke clip: 1.58 px -> 8.04 px against a true 8.0 px, i.e. 80% error
 down to 0.5%. End-to-end the pipeline's reported belt speed goes from 1.18 cm/s
 to 6.07 cm/s against a true 6.00 cm/s.

 THE SCALE IS A SEPARATE MATTER, and worth being explicit about because it is
 easy to misread. Pixel flow and cm/s are independent: 8.04 px/frame at 15 fps is
 120.6 px/s, and cm/s is that multiplied by a cm-per-pixel scale.

   --cm-per-pixel 0.05        ->  6.032 cm/s   the fixture's true scale
   --calibration calib_fixture.npz -> 7.479 cm/s   the checkerboard scale

 The 0.05 cm/px is the ground truth of the synthetic clip. The 0.062 cm/px implied
 by the checkerboard calibration is 24% larger, because the checkerboard fixture
 and the synthetic video are unrelated geometries - the calibration was fitted to
 2.5 cm squares on a board that has nothing to do with the boxes in the clip.
 Using it to scale the flow bakes in a 24% scale error that has nothing to do with
 the flow fix. So every speed accuracy claim in this section is quoted against
 the true scale, and the calibrated run is reported separately as an end-to-end
 integration check rather than as a flow-accuracy measurement.

 P2's RECOMMENDATION REVERSED: with the field fixed, the median is the better
 estimator and fit_affine_flow is now only a fallback for a degenerate field
 (all-zero or non-finite), because on the smoke clip it reads 7.52 px against
 the median's 8.03 px. The log's comparison was made on a broken flow field, so
 its conclusion did not survive the fix that preceded it.

 Farneback is retained only as a cross-check, reported in flow_metrics.json.

 9.6  P4  --  STATIC FALSE POSITIVES  -  FIXED, AFTER AN INCOMPLETE FIRST TRY
--------------------------------------------------------------------------------
 The log's evidence: the dark belt strip at (0,270) 640x90 is returned as a
 detection on every frame, with its centre at exactly (320.0, 315.0) on all of
 them, and it became track ID 1 measuring 39.69 x 5.50 cm.

 Step 1 - reject static measurements.
   Change : `reject_static_detections` drops a detection whose centre is within
            2 px of a detection in the previous frame. A box on a moving belt
            shifts 8 px/frame on the smoke clip, so a near-zero displacement is
            a reliable static-background cue. Wired into pipeline.py with
            --keep-static to disable.
   This works at the measurement level: the belt is correctly rejected on every
   frame from 1 onward.

 Step 2 - the track still appeared, and the first write-up of this fix claimed
          it did not. It did not. Measured:

              before any fix     3 tracks, 135 records
              after step 1       3 tracks, 121 records

   Track ID 1 was still there, merely cut from 45 frames to 31. The record count
   drop is easy to misread as "the false positive is gone" when in fact the
   phantom track survives and simply coasts out of its confirmation window
   sooner, because the measurements that would have kept it alive are gone.
   Suppressing a false measurement is not the same as suppressing a false track.

 Step 3 - the actual fix: do not create a track until moving is observable.
   On frame 0 there is no previous frame, so a static region and a real box are
   literally indistinguishable. The first measurement is therefore withheld
   from the tracker and detection starts on frame 1. One frame (67 ms at 15 fps)
   of latency is a far better trade than a 31-frame phantom track.

   Applied in both entry points, pipeline.py and module_d_tracking/kalman_tracker.py,
   because the standalone tracker is the module that produced the original
   finding and it was still emitting the false positive after step 1.

   A second, subtler bug surfaced while wiring this up: previous_detections must
   hold the RAW detections, not the post-filter list. Storing the filtered list
   means a detection rejected on frame N is absent on frame N+1, so the
   comparison finds nothing, re-admits it, and the track is created and dropped
   on alternate frames. That produced 22 tracks. pipeline.py already stored the
   raw list; kalman_tracker.py did not.

 Step 4 - the two entry points had grown their own copy of this decision, and had
          already drifted once (step 2's raw-vs-filtered bug existed in
          kalman_tracker.py and not in pipeline.py). Extracted as
          `select_tracking_detections` in module_a_segmentation/segmentation.py,
          which owns reject_static_detections, and both entry points now call it.
          The 2-px static threshold, the raw-vs-filtered rule and the
          first-frame withholding are defined once.

   VERIFIED that the new tests are load-bearing rather than decorative: deleting
   the first-frame withholding from select_tracking_detections makes
   test_static_background_never_becomes_a_track fail with 2 tracks instead of 1.
   A regression test that still passes against the broken code is what section
   2 criticised about the original suite, so it was checked rather than assumed.

 VERIFIED after step 3, smoke clip:
              before any fix     3 tracks, 135 records
              after step 1       3 tracks, 121 records   (phantom persists)
              after step 3       2 tracks,  88 records   (phantom gone)

   The two surviving tracks are the two real boxes, each present on 44 of 45
   frames - the missing frame is frame 0, which is the intended cost.
   --keep-static restores the original 3 tracks at 45 rows each, so the flag is
   not silently inverting the fix.

 Caveats, stated because they are real:
   - A genuinely stationary box is also dropped. On a moving conveyor that is
     the correct trade; on a stopped line it would suppress real detections.
     That is why it is a flag rather than unconditional.
   - A stationary object that starts moving is picked up one frame after it
     starts, not before.
